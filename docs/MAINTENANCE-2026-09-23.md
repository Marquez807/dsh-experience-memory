## 三、本次的三处改动

### 1. 本工作区第一次有了项目标识（`.dsh/memory.yml`）

`F:\dsh主工作区` 既不是 git 仓库根、也没有 `package.json`，所以在加这个文件之前，领域解析落到
最后一级「留空」——库里的记录**全是工作区级**，跨工作区印证这条路从未走通。新增的文件只声明了一行：

```yaml
domain: dsh-main-workspace
```

**实测生效方式（这一点我已核对，别读错）**：加上之后新写入的记录会同时带上这个领域名，但

- **`scope` 仍然是 `workspace`** —— 领域名是附加标签，不等于"立刻对所有项目可见"；
- 真正改成领域级、对同领域其它工作区可见，仍然要等**第二个不同工作区**独立报告同一条内容
  （`src/lifecycle.ts` 的晋升分支：`scope === 'workspace' && domain !== '' && corroborations >= 2`）。

实测证据（写入一条真实记录后直读库）：

```
{ "id": "267180af5bbd4452f3e9", "workspace_id": "d80b18919fe33321",
  "domain": "dsh-main-workspace", "scope": "workspace", "status": "confirmed" }
本工作区带领域的记录数：1 / 215
```

所以这次配置的**直接效果**是：领域标签从此写入每一条新记录，晋升这条路第一次具备了条件
（在此之前 `domain` 恒为空串，晋升分支永远不可能命中）。**晋升本身仍待第二个工作区印证**——
本次巡查里还没有发生，不作"已生效"表述。

子项目（各自有 `package.json` 或 git remote）仍解析到它们自己的领域，不受影响。

### 2. `tools/preview.mjs` 修好了

它此前跑完普查就抛 `TypeError: Cannot read properties of undefined (reading 'execute')`，
「这一轮会注入什么」这段从未输出过。两个原因，都不是插件的问题：

- 它只挂了 `systemPrompt` 与 `tools` 两个服务，而插件声明 `inject: ['tools','systemPrompt','commands']`
  ——少一个服务，插件挂载但**静默不激活**，于是 `memory_recall` 根本没注册（与 `tools/verify-install.mjs`
  的三件套对齐后修复）；
- `.get()` 的返回值没做检查，所以缺工具时是崩溃而不是报告缺工具（现改为报一行说明后继续）。

同一处还修了两个样本形状问题：会话对象改用真实读法 `snapshotEvents()`（真实 Session 上没有 `events`
属性——`src/session.ts` 记录了这次教训），并补上 `header.agentPreset`。

### 3. 一条"误注入"报告被撤回

巡查中我一度认为「查询『继续』命中了广东工伤保险记录」是子串误撞，准备改判据。**先写复现测试就发现
这个结论是错的**：那条记录正文里本来就有「继续」，命中是真的。随后两次尝试制造真正的误撞都失败，
实测分词给出了原因：

```
tokenize('继续')   -> ['继续']          二字词保持整词
tokenize('后续期') -> ['后续','续期','期']  里面没有 '继续'
```

单字保持单字、二字保持整词，所以查询词不可能跨过它并不包含的边界匹配上。**判据没有修改**，
只新增了一条带正对照的回归测试把这个一致性钉住（`tests/retrieve.test.ts`）。

### 4. 投递层第一次有了痕迹（本次巡查最重要的发现）

巡查随后暴露出更靠前的一层问题：**经验有没有被送到，此前查不到。** 投递只看工具参数里的标识符
（中文参数值一个都抽不出来），而且不写库、不写日志。于是"经验没用"和"经验根本没送到"在账上完全一样。

本次为此加了 `delivery` 表（schema 6）、拦截账的四分类、以及普查/`/memory-status` 的投递统计。
**判据一个字没改**——原因、实测数字与下一个判据的预注册门槛，见 [`DELIVERY-GAPS.md`](DELIVERY-GAPS.md)。
