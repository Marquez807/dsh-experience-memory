## 二、五条问题（G1–G5），每条一个可证伪主张

### G1 适用性：什么时候该用这条经验？

- **主张**：**索引可以从写入时的解题轨迹里自动归纳出来**，不必人手写。依据是 CBR 综述的原话——
  程序员写死索引会得到"an inflexible system that cannot adapt to new domains"，而
  **"问题求解领域特别适合（从轨迹归纳），因为解题行为的轨迹（目标树）本身就是现成的索引信息"**。
  `recall_for` 正是这条路线的**人工版**，缺的是自动版。
- **落地**：写入时把"这次调用点了哪个文件/哪个工具/哪条命令"从轨迹里抽出来，**提议**成 `recall_for`，
  由写记录的人确认（不是自动写死）。
- **验收（可证伪）**：30 条已有 `recall_for` 的记录上，自动推导与人工写的**路径级一致 ≥70%**。
  **<40% 则确认"必须手写"**，墙 5 无解，152 条静默是死账。

**判据补充（2026-09-25 深夜，在跑之前写死，不许事后放宽）**：

1. **样本量条款**。目标写的是 30 条，但真库里自己声明过锚点的只有 48 条，两边可比对的只会更少。
   所以先说清怎么读：**N<10 判"未答"**（这一点样本回答不了"机器能不能替代手写"，宁可没结论）；
   **10≤N<30 只报"方向性读数"，不算通过**；**N≥30 才按 ≥70% / <40% 判过与不过**。
2. **比的是路径级**：`path:` 只比**小写 basename**（`a/b/x.ts` 与 `x.ts` 算同一条），
   `tool:` / `command:` 精确比。一条记录两侧只要有**一个**共同锚点即算一致；另报交并比作强度参考。
3. **机器那一侧必须是"真提"**，不许从题干抄答案。两个坑都在 `tools/anchor-agreement.mjs` 里挡掉：
   - `backfill-anchors.mjs` 默认**跳过**已声明锚点的记录，拿默认输出的提案文件比，交集按构造为空
     ⇒ 必须用 `--include-declared` 重新生成；
   - 该选项下提议只读 trigger 的**散文一半**（`--- anchors ---` 之前），否则它会读到人写的
     `path:wipe.mjs` 然后"提议"出同一个锚点——那不是一致，是把答案写进题干。

**怎么跑**（只读，不写库）：

```
node tools/backfill-anchors.mjs --cwd F:\dsh主工作区 --include-declared --out tools/proposed-anchors-all.json
node tools/anchor-agreement.mjs --cwd F:\dsh主工作区 --out docs/g1-anchor-agreement.md
```

（写成 `proposed-anchors-all.json` 而不是覆盖原来的 `proposed-anchors.json`：后者是**跳过**已声明锚点
那一版的存档，两个文件的含义不同，混用就会得出"交集为空"的假结论。）

**结论（2026-09-25 深夜，跑完之后填）**：见 `docs/g1-anchor-agreement.md` 与本文件下面这节。

#### G1 结果：**只作方向性读数**（样本 14 < 30，不算通过也不算失败）

完整读数与逐条清单：`docs/g1-anchor-agreement.md`。要点：

| 数字 | 值 |
|---|---|
| 自己声明了锚点的记录 | 50 条 |
| 提案文件里的记录 | 24 条 |
| **两边都有（可比对样本）** | **14 条** |
| 一致（路径级有交集） | **11 / 14 = 78.6%** |
| 交并比均值 | 0.595 |

**按事先写死的样本量条款，这一档只能说"倾向能自动"，不能说"通过"。** 一个 14 条样本上的 78.6%
撑不起"机器可以替代手写"这种结论——它离 40% 与 70% 两条线都还有距离，换几条记录就可能翻。

**更要紧的是：三条不一致里有两条说明"一致率"这个判据本身不够好**（逐条见下）：

1. `5fbfe48f`（"路径锚点别用到处都是的裸名字"）：**机器提的是 `path:tools.js`**——
   正是这条记录自己警告的那种裸名字；人写的是 `anchors.ts` + `t2-scenarios.json`。**这条是机器错。**
2. `c26aea99`（"含中文的 .ps1 必须带 BOM"）：人写的是 `command:executionpolicy`，
   机器提的是 `path:run_all.ps1`。**这条更像是人写得不好**——`-ExecutionPolicy` 是个到处都出现的
   参数，按 `anchorCostMaxHits=300` 那条规矩，这种锚点本来就该被拒。
3. `ed6e6e66`（"quant worker 是常驻进程"）：人写 `path:worker.js` + `command:run_all.ps1`，
   机器提 `path:cli.py`。两边都在理，只是指的不是同一个文件。

**所以真正的结论不是"78.6% 所以能自动"，而是**：

- **一致率高估了机器**：它只看"两边有没有撞上同一个文件"，而撞上不等于这条锚点**该不该触发**。
  第 1 条就是反例——机器准确复现了这个记录要防的错误。
- **一致率也低估了人**：人写的锚点里也有过宽的（第 2 条）。
- **两边都不是标准答案**。标准只有两条，而且都已经有了：
  ① **成本**——`tools/anchor-cost.mjs`，命中 ≥300 次就拒（`anchorCostMaxHits`）；
  ② **效果**——受控删除测试（G2）。**"两边一致"只是它们的廉价代理，不能当终点。**
- **样本为什么这么少**：提案要求记录声明字段里点名了**工作区里真实存在**的文件。
  50 条声明了锚点的记录里只有 24 条满足，交集 14 条。**样本量不够的直接原因是提议规则太窄**，
  不是"记录太少"——这一点要单独修才有下一次读数，别用放宽判据来掩盖。

**下一步（不要跳过）**：拿这三条不一致去量成本（`anchor-cost.mjs`），看机器提的那个
`path:tools.js` 到底命中多少次——如果远超 300，这就是"提议规则需要加一道成本闸门"的直接证据。

#### G1 结果之二：量了成本之后，**"一致率"这个判据基本没用**

`node tools/anchor-cost.mjs path:tools.js path:anchors.ts path:t2-scenarios.json command:executionpolicy path:run_all.ps1 path:cli.py path:worker.js`
（语料：15,896 次真实调用；门槛 300）：

| 锚点 | 命中 | 谁写的 | 读法 |
|---|---|---|---|
| `path:tools.js` | **526** | **机器** | ❌ 超门槛——机器提的锚点被我们自己的成本闸门拒 |
| `path:cli.py` | **485** | **机器** | ❌ 同上（另一条不一致里机器提的） |
| `path:run_all.ps1` | **572** | **人** | ❌ 超门槛——人写的锚点**同样**被拒（两条记录都用了它） |
| `command:executionpolicy` | 116 | 人 | ⚠️ 偏高 |
| `path:worker.js` | 100 | 人 | ⚠️ 偏高 |
| `path:anchors.ts` | 25 | 人 | ✅ |
| `path:t2-scenarios.json` | **0** | 人 | ⚠️ **从来不触发**——等于没声明 |

**三条不一致里，两边写的锚点都过不了我们自己的成本闸门。** 所以：

- **一致率既高估机器也高估人**：它只问"两边有没有撞上同一个文件"，不问这条锚点**该不该触发**。
  第 1 条里机器准确复现了那条记录自己要防的错误（裸名字 `tools.js`）；第 2 条里人写的
  `command:executionpolicy` 也偏宽；还有一条人写的锚点命中 **0** 次，等于白声明。
- **真正能判的是成本与效果**，而这两样都已经有工具：`anchor-cost.mjs`（命中 ≥300 拒）与
  受控删除测试（G2）。**"两边一致"只是它们的廉价代理，不能当终点。**

### G2 效果回路：这条经验防住了错吗？

- **主张**：**别从文本判断，去测**——把那一轮重放、**拿掉这条记录**、看结果变没变。
  变差＝必需，没变＝冗余。（《Hindsight Memory-PRM》的核心机制，它证明**干预式归因优于观察式归因**，
  这正是我们词共现失败的那条。）
- **落地**：`tools/verified-user-ab/` 的双臂跑法**就是**受控删除测试。扩成通用工具：
  给定一个回合 + 一条记录，跑 有/无 两臂，比产物。
- **验收**：20 个真实回合上，删除测试的二分判定与人工判定**一致率 ≥80%**，且同回合重复 3 次判定一致。
  **<60% 则这条路线作废**，"效果不可量"的结论保留。
- ⭐ **这一条会翻转我们现在的结论**（详见第四节）。

### G3 记忆演化：记录怎么被修正、合并、分化？

- **主张**：**后台巩固**（去重/合并/冲突冻结）+ **再巩固**（被回忆的记忆变可塑、可更新）。
- **落地**：`agent/turn-stopping` 的维护轮次里加一道"睡眠期合并"，把同一教训的多条记录合一条。
- **验收**：合并跑 N 轮后，**检索到的条目数下降 ≥30% 且 A/B 正确率不降**。
- ⚠️ **证据强度五条里最弱**：ZenBrain 与 NOUS **都没有对照实验**（NOUS 只报首个运行周期的初始数据、
  且自承只是"定性相关"）。所以这条**排在最后**，而且落地前必须先用自己的判据验，不许照搬。

### G4 技能固化：经验怎么从"要读的文字"变成"不用想的反射"？

- **主张**：**多对一地合并**成一条可移植的规程，胜过逐条检索片段式记忆。Trace2Skill 实测
  **一条蒸馏出的技能胜过 ReasoningBank 式逐条经验检索**，且并行合并强于顺序编辑、跨模型可移植
  （Gemma 演化的技能提升 Qwen）。
- **落地**：同一教训出现 **≥3 次**后，把它们合成一条 SOP 记录（我们已有 `superseded_by`，
  但那是"新的取代旧的"，不是"多条合成一条"）。
- **验收**：找一组"同一教训 3 条以上"，合并成 1 条 vs 保留 N 条，**同预算**下合并版**至少赢 1 个场景**。

### G5 抗膨胀：成长时不退化、不失焦？

- **主张**：记忆该保留**"会影响决策的那些区分"**，而不是"忠实的描述"。DeMem 把这写成决策中心的率失真，
  给出**精确的遗忘边界**：**只在数据证明"合并会导致决策冲突"时才细分**。
- **落地**：这是**对我们设计的批评**——`importance()` 与退役规则现在用的是描述性标准
  （证据等级/复用次数/陈旧度）。改成按**决策损失**：不影响决策的，忘。
- **验收**：**同样字节预算下**，按决策损失保留 vs 按复用次数保留，真实任务正确率**赢 ≥5%** 才算成立。

## 三、五条收敛到一个回路（这是本篇的主要结论）

**G2 的"受控删除测试"是另外四条的地基。**

| | 用删除测试做什么 |
|---|---|
| **G2** | 量效果：删了会不会变差 |
| **G5** | 定遗忘边界：**不影响决策的，就该忘** |
| **G1** | 学索引：**什么时候删了会变差**＝这条记录的适用范围 |
| **G4** | 找冗余：**删谁都不变差的几条**＝该合成一条 |
| **G3** | 判何时再巩固：**删除效应变了**＝记忆该更新 |

所以"成长型"不是五个功能，是**一个回路**：

> **测（删除测试）→ 标（从轨迹归纳索引）→ 合（多对一合并）→ 忘（决策边界）→ 再测**

我们目前只做了**"标"的一半**（手写 `recall_for`）和**"忘"的一半**（按复用计数）。
**"测"是缺的那一环，而且它是另外三个环节的输入。**

## 四、先做哪一步：**受控删除测试**（G2）

**按"能不能翻转既有结论"排序，这一条排第一。**

我们现在最强的一个负结论是：**"失败覆盖率量不出来"**（§5 的撤除条、§20）——理由是分子需要语义判断，
而词共现代理会算错。**受控删除测试恰恰绕开语义判断**：它不问"这条该不该拦住那次失败"，
而是"**拿掉它，结果变了吗**"。

- **如果它成立** ⇒ "效果不可量"这个结论**被翻转**——不是不可量，是**不能靠文本量、只能靠实验量**。
  同时 G1/G4/G5 三条的输入就有了。
- **如果它不成立**（一致率 <60%）⇒ 我们就拿到了一个同样重要的负结论：**连干预式都量不出来**，
  那"成长型"这个目标本身要重新定义。**这是能翻转方向的实验。**

**基础设施已经有了**：`tools/verified-user-ab/` 的双臂跑法、隔离 home、带守卫的清库脚本、
从文件系统判产物的判据。要做的是把它**从"一个场景的 A/B"变成"给定回合 + 给定记录，跑 有/无 两臂"** 的通用工具。

**具体验收**（写死，先声明后跑）：

1. 取 **20 个真实回合**（从 `tools/session-calls.py` 抽的语料里选，含"有过投递"的）。
2. 每个回合 × 每条相关记录，跑**有/无**两臂（各 3 次以排除采样噪声）。
3. 判定"必需/冗余"，与**人工二分判定**比：**一致率 ≥80% 且同回合 3 次一致**才算通过。
4. **<60% 判为失败**，结论翻不转，"效果不可量"保留。

## 五、明确不做的（防摊大饼）

1. **不上向量/稠密检索。** 成本高，且竞品实测（`dsh-evolve`、`kovey`）证明它**没解决适用性问题**——
   无关记录照样得分更高。先把"适用性"的理论问题想清楚再谈工具。
2. **不做"自动改写已有记录"。** G3 的再巩固是有诱惑力的方向，但它证据最弱（两篇都无对照），
   而且自动改写会破坏 `verified-user`/`verified-file` 的证据链——**记录可以被取代，不能被偷偷改**。
3. **不在这一步谈 G3/G4。** 顺序是 **G2 → G1 → G5 → G4 → G3**，因为每一步都吃上一步的输出。
   跳着做会做出一堆没有反馈信号的机制。
4. **不估算"省了多少 token"。** `dsh-negative-ledger` 主动拒绝估这个数，理由成立：估不准且会被当成绩。

## 六、这一轮的验收（对照计划）

| 计划要求 | 状态 |
