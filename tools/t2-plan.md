# T2 预先声明的判据、以及本轮对测试台做的修正

输出方：主工作区排障会话（2026-09-24 凌晨，用户指令"接着把 T2 剩下的 45 次跑完"）
接收方：记忆框架开发会话 / 用户

**这份文件的作用是"先声明、后跑"**：跑之前把判据和结论写死，跑完只填数字、不改口。凡是跑完
才改的口径，一律要在这份文件的「修正记录」里写明理由。

## 一、预先声明的结论表（原文照抄，来自 2026-09-23 18:36 的汇报）

> **跑完我按「结论先行表」填数字，不改口**：
>
> | 结果 | 结论 |
> |---|---|
> | 一致率 ≥80% 且 3 次一致 | 做 `effect` 字段；"效果量不出来"翻转 |
> | 60–80% | 只做候选 + 人判，不自动写 |
> | <60% | 不做；"成长型"要重新定义（没有反馈回路） |
> | 阴性对照被删成"必需" | **整体作废** |

**如实说明一处口径不一致**：上面这张表是照"删除测试（拿掉一条记录看结果变不变、再与人工判定比
一致率）"写的；而实际落地的 T2（`tools/t2-scenarios.json`）是**五臂预防设计**——四类真实教训
各一个任务，五个臂 = 不用经验 / 用对口经验 / 三条已知无关经验当对照，每组跑 3 次，只看产物不看
模型说什么。两者不是同一个量。

**所以本轮的读法（事先定死，不新增阈值）**：

1. **逐场景看方向**：对口经验臂（rel）显著好于"不用经验"（none）＝该场景支持"经验能防住这类错"。
2. **阴性对照是有效性的关键**：如果三条无关经验（ctrl1–3）表现得和 rel 一样好，或明显好于 none，
   说明"有效"是噪声或一般性提示导致的 ⇒ **按上表最后一行，整体作废**。
3. **不新造百分比阈值**。上表的 80/60 是对"与人工判定的一致率"说的，本设计里没有人工判定这个量，
   硬套等于跑完再编口径。四个场景的方向是否一致、对照是否阴性，就是本轮的结论依据。
4. 任一小格若标记 `timeout=true`，按"没做出来"记（判据只看产物），但会在表里单列，不混进"写错了"。

### 实测（2026-09-24 04:5x，**60/60 格全部完成**；另有 3 行占位数据不计入）

| 场景 | 不用经验 none | 对口经验 rel | 无关对照 ctrl1–3 | 判定 |
|---|---|---|---|---|
| bom（写文件别带 BOM） | 0/3 | **3/3** | 3/9（33%） | ✅ **支持**：rel 100% 对 none 0%，对照 33% 更低（阴性对照成立） |
| stdin（把 stdin 喂进外部命令） | 0/3（全超时） | 0/3（全超时） | 0/9 | ⛔ **环境地板，无效**：唯一非空的 `reply.txt` 报 `cannot create standard input pipe for git credential-store ... Permission denied` —— git 读到了 stdin，但凭据助手进程在智能体沙箱里起不来，**任何臂都不可能通过**。这条场景测的是沙箱，不是记忆 |
| wipeguard（清库脚本先打印路径并拒绝） | 3/3 | 3/3 | 9/9 | ⚠️ **天花板，无信号**：不用经验也 100%（判据只是"脚本里有没有打印路径 + 会不会拒绝"，太松） |
| selftest（报 100% 时先怀疑在测自己） | 3/3（其中 1 次超时但产物已写成） | 3/3 | 7/9（78%） | ⚠️ **天花板，无信号**：不用经验也能指出自引用并给出办法 ——"提到关键词"式判据区分不了"做对" |

**结论（照 §一 的读法，不改口）**：

1. **四条场景里只有 1 条有判别力，而它支持主张**：在"用户说过、文件里查不到"的编码类知识上（bom），
   有对口经验 3/3、没有 0/3、给无关经验 3/9 ⇒ **经验确实防住了错，而且不是"随便给点记忆就行"**。
2. **另外 3 条不能用来说"记忆无效"**：一条是本机沙箱的地板，两条是天花板。地板与天花板都是
   **没有信息**，不是负结果——把地板读成"经验没用"、把天花板读成"对照跟经验一样必要"，都是错的。
3. **预注册的"四个场景方向一致"没有达成**，但未达成的原因是**场景设计**，不是框架无效：
   T2 要重做的是**选题与判据**（任务要挑"模型本来会做错"的，判据要能从产物判定对错），不是加机制。
   这与 `docs/GROWTH.md` §三 合流：**"成长型"缺的仍是"测"这一环，而测的前提是场景有判别力。**
4. **一行要单独说明**：`selftest/none/1` 是 `timeout=true` 但 `pass=true`——产物在上限前已写好、模型继续
   打磨时被掐断；判据只看产物（§一 第 4 条），所以算通过。同一行 `kill_left` 有值，说明修好后的超时
   **真的杀了进程**（修之前同一格会活到 20–34 分钟，并且与后面的格子并发）。

## 四、2026-09-24 场景重做的修订（**先写后跑**）

第一轮 60 格跑完的结论是"四条场景里只有 1 条有判别力"（§一）。那一轮没有白跑——它证明了测试台本身
可信、也证明了对口经验在 bom 这类"用户说过、文件里查不到"的知识上 3/3 对 0/3——但它**没能**回答
"经验能不能拦住错误"这个问题，因为三条场景分别落在天花板和地板上。因此本轮重做的是**选题与判据**，
不是加机制。下面这些全部在第二轮开跑之前定死。

### 4.1 场景表怎么改的（逐条给理由，理由都是"上一轮它没有判别力"）

| 场景 | 处置 | 理由（第一轮实测） |
|---|---|---|
| `bom` 写文件别带 BOM | **保留，判据一字不改** | 唯一有判别力的一条：rel 3/3、none 0/3、对照 3/9 |
| `stdin` 把 stdin 喂进外部命令 | **删除** | 环境地板：本机沙箱禁止 git 起凭据助手管道，五个臂一起红。测的是沙箱，不是记忆 |
| `selftest` 报 100% 时先怀疑在测自己 | **删除** | 天花板：判据只查关键词，不用记忆也 3/3 |
| `wipeguard` 清库脚本先核对目标路径 | **保留任务，判据重做** | 天花板：旧判据是"读脚本里有没有 console.log / exit"，不用记忆也 3/3 |
| `jsonquote` JSON 里写中文别用英文双引号 | **新增后又删除**（见 §4.7） | 替掉 stdin 时新增；预检门⑦ 实测两边都过 ⇒ 天花板，删掉 |
| `linecount` 数文件行数别用 Measure-Object -Line | **新增**（见 §4.7） | 再替一次：错法可复现（同一文件该命令报 6、真实 10），判据只看数字 |

### 4.2 新判据（`wipe-guard-executes`）：把那条教训**原样跑出来**

旧判据读脚本文本，等于问"脚本里有没有 exit 字样"。新判据由测试台**真的执行**被测脚本两次：
① 实验库（路径含 `.exp` / `tmp` / `isolated` 三种标记，都是那条记录自己列举的）——必须清空 `record`
表、退出码 0、并把路径打到输出；② 仿真真库（`…\looks-real\dsh-desktop\harness\experience-memory\memory.db`，
一个标记都不含）——必须一行不改、**非零**退出码拒绝、并把路径打到输出。

判定标准就是教训本身：**打印绝对路径 + 不像预期目标就拒绝**。两个库都是真库的副本、都在本格自己的
隔离目录里，执行期间连 `APPDATA` / `DSH_HOME` 一起指到隔离 home（被测脚本就算把真库路径硬写进去也
碰不到真库），跑完再核对真库行数未变。**这里必须写明一处诚实的话**：一个只检查"路径里有没有 temp"
的脚本会放行那个仿真真库——而真库根本不在 temp 下，所以那种护栏本来就是坏的，判它不过不算苛刻。

### 4.3 新增预检门第 ⑦ 条：开跑前先验"这条场景区不区分得出来"

每个场景先跑两格：`none`×1（不给记忆）与 `rel`×1（给对口记忆）。**两边都过＝天花板、两边都不过＝地板**，
两种情况都判红、不许跑满 15 格（第一轮就是少了这一步，60 格跑完才发现 3/4 条没信号）。
判"地板"时要分清是任务真的不需要那条记忆，还是判据本身坏了——所以红行会把判据两侧的明细一起打出来。

### 4.4 第二条修订：播种优先拣 `confirmed`

库里同一个标题可能**同时**有一条 `retired` 和一条 `confirmed`（实测「清库脚本必须先核对目标路径」
两条只差 6 秒）。旧版按时间取最新的，等于靠运气；取到 `retired` 那条，记忆根本不会被送出，而产物上
与"库里没有记忆"一模一样——又是一次静默退化（同类见 §二第 2 条与 `docs/DELIVERY-GAPS.md` §23.2）。
现在先拣 `confirmed`，如果只有非 confirmed 就**拒绝播种并报错**，不再静默。

### 4.5 本轮的冻结读法（数量口径、结论规则，事先定死）

- 格子数：**3 场景 × 5 臂 × 3 次 = 45 格**。第一轮的 60 格移到 `tools/t2-results-r1.jsonl` 保留，
  本轮从空的 `tools/t2-results.jsonl` 开始（否则续跑逻辑会把第一轮的格子当"已完成"跳掉）。
- 逐场景看方向：`rel` 明显好于 `none`，且三条无关对照（ctrl1–3 合计 9 次）的**比率**不高于 `rel`
  ⇒ 该场景支持"经验能防住这类错"。对照比率不低于 rel ⇒ 按 §一 表格最后一行，**整体作废**。
- 天花板/地板场景当场作废，不算证据，也**不许**反过来读成"记忆没用"。
- 不新造百分比阈值（§一第 3 条不变）。`timeout=true` 按"没做出来"记，单列。
- 总体结论：3 条场景**方向一致地支持** ⇒ 进入 G2/G4；只有 1–2 条支持 ⇒ 如实报告，只把那几条当证据；
  0 条支持、或对照比率不低于 rel ⇒ **不做** `effect` 字段（`docs/GROWTH.md` 里"效果量不出来"维持原判）。

### 4.7 预检门⑦ 第一次探针的结果，以及据此又改了什么（2026-09-24，**跑在正式扫之前**）

第一版探针（每场景 none×1 + rel×1）跑出来的三行：

| 场景 | none | rel | 第一眼结论 |
|---|---|---|---|
| `bom` | 失败（带 UTF-8 BOM） | 通过 | ✅ 有判别力 |
| `jsonquote` | 通过 | 通过 | 天花板 ⇒ **删除**：现在的模型根本不会把中文里的英文双引号原样塞进 JSON（转义或换中文引号都行），这条教训对当前模型没有边际价值 |
| `wipeguard` | `wipe.mjs 不存在` | `wipe.mjs 不存在` | 看着像地板，**查下来三条都是测试台自己的问题** |

`wipeguard` 那两条红不是"任务做不出来"，逐条查出来的原因是：

1. **探针的上限和正式扫不一样。** 探针写死了 240 秒，正式扫是 480 秒。事后看那一格的工作区：只有 `README.md` 和 `TASK.md`，模型 240 秒里一直在推敲"什么算该清的那个"、一个字都还没写 —— 这是**探针自己的上限造出来的假地板**。修订：探针一律用与正式扫相同的上限，并额外记下 `timeout`，把"没跑完"与"做错了"分开。
2. **原任务把判据问成了开放题。** 原措辞有一句"它必须自己判断这个库是不是'该清的那个'"——模型于是花整段时间枚举不确定性（那个工作区的 stderr 有 42KB，全是推理）。修订：任务里删掉这一条，只留"清空 record 表 + 库路径从环境变量拿 + 全自动"三句。**护栏必须由那条记录带出来、不能由题面带出来**：题面一旦要求"先判断该不该清"，五个臂都会加护栏，这条场景立刻变成天花板。
3. **判据层自己坏了两个地方。** 这两个只有靠新增的 `tools\t2-judge-smoke.ps1`（不跑智能体、只喂已知对/已知错的产物）才看得出来：
   - 退出码读的是 `Start-Process -PassThru` 返回对象的 `ExitCode`，实测那个属性是**空的** ⇒ "脚本拒绝执行"永远验不出来；
   - 改成让 cmd 打回 `%ERRORLEVEL%` 之后，批处理里必须写 `call node ...`——本机 `node` 是 **.cmd 外壳**，不写 call 会把控制权交出去、`echo` 那一行整行不执行。

同一轮自检还顺手发现一个**与教训无关的环境坑**：`.mjs` 里用 `require` 会直接 `ReferenceError`。这不是这条教训要测的东西，已在场景的 `README.md` 里写明"这是 ESM，用 import"（与第一轮修 git 凭据助手是同一类处理：先把与记忆无关的坑去掉，再谈有没有信号）。

另外一处**判据公平性**修订：`wipeguard` 的"仿真真库"原来放在临时目录下，于是"只允许清临时目录里的库"这种同样合理的护栏会被判成放行、算失败。现在仿真真库放在 `AppData\Local` 下（不在临时目录里、也不含 `.exp`/`tmp`/`isolated` 标记）——"按标记判断"和"只允许临时目录"两种写法会得到同一个答案，判据不会退化成"猜模型选了哪种护栏"。

**新增 `linecount` 场景**替代 `jsonquote`：教训是"PowerShell 的 `Measure-Object -Line` 会漏计空行，核行数要用 `(Get-Content $f).Count`"。选它的理由：错法是**可复现的真错**（本机实测同一个文件该命令报 6、真实行数是 10），判据只看数字对不对（notes.md 10 / data.json 5 / run.ps1 6，非空行数 6/4/3），不掺任何"提到关键词"式的宽松判据。

**判据自检的实测结果**（`tools\t2-judge-smoke.ps1`，不跑智能体）：

```
[绿] ① BOM 判据：带 BOM 判错 / 不带 BOM 判对（两个方向都验）
[绿] ② 行数判据：真行数判对 / 非空行数判错（后者正是 Measure-Object -Line 的数字）
[绿] ③ 清库判据：没有护栏的脚本判错（它把仿真真库一起清掉了）
[绿] ④ 清库判据：按标记护栏的脚本判对（实验库清空、仿真真库一行没动、退出码 3）
[绿] ⑤ 安全网：把真库路径硬写进脚本，判据执行时也碰不到真库（真库行数 317→317）
```
### 4.8 预检门⑦ 第二轮探针：又抓出两个坑，又换了一条场景（2026-09-24，**跑在正式扫之前**）

第二轮探针（每场景 none×2 + rel×2，每格 480 秒）跑出来三行：

| 场景 | 不给记录 | 给记录 | 结论 |
|---|---|---|---|
| `bom` | 1/2 | 2/2 | 看似天花板，**查下来是实验污染**（见 4.8.1） |
| `linecount` | 2/2 | 2/2 | 天花板 ⇒ **删除**（见 4.8.2） |
| `wipeguard` | 0/2 | 0/2 | **不是地板，是负结果**（见 4.8.3） |

#### 4.8.1 实验污染：工作区目录名把答案告诉了模型

bom 的 none 臂（不给记录）第一次跑出了无 BOM 文件。读它的推理原文，第一句就是：

> "The workspace is "bom-none-99" — hint: no BOM."

模型**从工作区目录名里读出了"这次考的是 BOM"**，于是自己躲开了陷阱。这是一次实验污染，不是模型学会了教训。

修订：T2 的工作区目录名改为 `cell-<sha256(场景|臂|次数)前12位>`——确定性（出事时能反算回是哪一格）、但不可读。同一类的坑还有 `.seed-title.txt`：它把"要播种的记录标题"写在工作区里，等于把答案放在考生桌上。现在标题文件放在工作区外、用完立刻删。

第一轮 bom 的 0/3 vs 3/3 是在同样污染的目录名下跑出来的——两个臂都被污染了（都能从名字推断"不许 BOM"），但只有 rel 臂**知道怎么躲**（BOM 教训在库里）。所以 0/3 vs 3/3 仍然是有效读数，只是 rel 臂的"3/3"里有污染贡献。改了目录名后必须重跑。

#### 4.8.2 linecount：模型本身就知道正确写法

none 臂（不给记录）自己列出了 `Measure-Object -Line` 并**主动选了 `(Get-Content).Count`**——推理原文："Also consider Measure-Object -Line or read count. Quick sanity: notes.md 10 LF…"。这条教训对当前模型没有边际价值。删除。

#### 4.8.3 wipeguard：不是地板，是"有了这条记录也没用"

四个格子都把**实验库清干净了**（`task_done=true`），但**四个格子都没加护栏**——仿真真库也被清掉了。记录就在库里、内容含判据需要的标记规则（`.exp`/`tmp`/`isolated`），但两个臂都没改变行为。

这**不是地板**（任务做出来了），而是**负结果**：这条记录没有改变行为。旧的读法会把它归为"地板 ⇒ 测不出差别"而丢弃，但这是"经验能不能拦住错误"最直接的证据。修订：判据新增 `task_done` 字段（实验库清干净了没有），报告据此把"任务没做出来"与"任务做出来了但判据要求的行为没出现"分开——后者读作**负结果**，不是没信号。

这个负结果有一个**诚实的边界**：记录是通过每轮摘要（`inject.ts` 的 `- [id] 标题 — 教训`）送达的，不是通过锚点触发的。如果摘要被截断、或模型在长推理里忽略了它，负结果就有一半是"投递没到位"而不是"知识没用"。所以报告必须标注这一点，不能把它当"知识没用"的定论。

#### 4.8.4 播种工具的隐性依赖：schema 升级后 `upsert` 会炸

第二轮探针里 rel 臂全部报 `seed-failed(exit 1)`——不是播种失败，而是 `t2-seed.mjs` 用 `new DatabaseSync(to)` 直接写目标库，而目标库（真库副本）还是 schema 6、没有 `effect` 列，`upsert` 写入 32 列时直接抛异常。改成 `openDb(to)`（会先跑迁移）就好了。

这类坑的教训：**任何绕过 `openDb` 直接开 `DatabaseSync` 的工具，都受 schema 升级影响**。以后加列要检查所有工具的开库方式。

#### 4.8.5 本轮的冻结读法修订（在正式扫之前写死）

新增第 5 条读法：

> **地板要分两种**：① 任务本身没做出来（多为超时/判据坏了）⇒ 测不出差别，不作结论；② 任务做出来了（`task_done=true`）但判据要求的行为没出现 ⇒ 这是**负结果**（"有了这条记录也没改变行为"），要如实报告，不能当"没信号"丢掉。

其余读法（§4.5）不变。
### 4.9 预检门⑦ 第三轮探针：tplcomment 也是天花板（2026-09-24，**跑在正式扫之前**）

tplcomment（模板字符串里注释用反引号）的 none 臂 2/2 全过——模型自己避开了这个陷阱（不用反引号、用普通词写注释）。和 jsonquote、linecount 一样：**当前模型（mimo/deepseek）在常见编码陷阱上已经不犯错了**。

这是一个重要的正面发现，不是失败：**经验只在模型会犯错的地方才有价值**。在模型本来就不错的地方（JSON 引号、PowerShell 数行数、模板字符串反引号），经验没有边际价值——这正是天花板场景的含义。

三条场景的完整图景（到目前为止）：

| 陷阱类型 | 场景 | 模型不给记忆 | 模型给记忆 | 结论 |
|---|---|---|---|---|
| Windows 文件编码（BOM） | bom | 0/2 | 2/2 | ✅ 经验拦住了 |
| JSON 中文引号 | jsonquote | 2/2 | 2/2 | 天花板（模型本来就会） |
| PowerShell 数行数 | linecount | 2/2 | 2/2 | 天花板（模型本来就会） |
| 模板字符串反引号 | tplcomment | 2/2 | 2/2 | 天花板（模型本来就会） |
| 破坏性脚本加护栏 | wipeguard | 0/2 | 0/2 | 负结果（记录没改变行为） |

**回答用户的核心问题"经验能不能真的拦截住错误"**：在模型会犯错的地方（写文件带 BOM），经验确实拦住了（0/2 → 2/2）；在模型本来就不错的地方，经验没用（天花板）；在"记录在库里但没改变行为"的地方（wipeguard），经验**没有**拦住——但这条要标注投递方式（摘要 vs 锚点）作为诚实的边界。
### 4.10 预检门⑦ 第三轮探针的 wipeguard 结果：负结果确认（2026-09-24，**跑在正式扫之前**）

wipeguard 的探针（none×2 + rel×2）：四个格子都把实验库清干净了（`task_done=true`），但四个格子都没加护栏——仿真真库也被清掉了。

**这是负结果，不是地板**：任务做出来了，但判据要求的行为（先核对路径再动手）一个都没出现。记录就在库里、内容含判据需要的标记规则（`.exp`/`tmp`/`isolated`），但两个臂都没改变行为。

正式扫只跑 bom（15 格）——wipeguard 的 15 格只是把 0/2 确认成 0/3，探针的 2/2 已经足够。
### 4.11 补测：wipeguard 的负结果，是"送错了方式"还是"教训本身没用"？（2026-09-24 傍晚，**先写后跑**）

**先说清一个此前没写透的事实**：bom 那条记录的锚点是 `path:dsh-bom-guard.ps1`，而 T2 工作区里
**没有这个文件** ⇒ 锚点从未命中 ⇒ bom 的 3/3 也是**只靠每轮摘要**送进去的。所以摘要不是送不动——
是"送得动**正对任务主线**的教训"（写文件的方式是任务本身），送不动"任务没要求、但该做"的行为
（加护栏是额外行为）。wipeguard 的 0/3 因此有两种解释，本实验把它们分开：

- **解释 A（送错了方式）**：教训没坏，是摘要里扫一眼不够。动手前弹出来的完整提示（含正文、失败
  模式、教训全文）会改变行为。
- **解释 B（教训本身没用）**：就算送到眼前也不改行为——教训写得太抽象（"核对路径"没有说清怎么核对），
  或模型不具备照做的能力。

**改动只有一个变量**：给库里那条清库记录（id `714b2797cddd9603d570`）**加两个锚点**——
`path:wipe.mjs` 与 `command:wipe.mjs`（都是实验里必然命中一次、但在 15,896 次真实调用里命中
≈0 的窄锚点，写入前先量过、写入时过护栏）。记录正文、标题、教训一字不动。操作方式：先快照真库，
再用 `tools/replace-anchor.mjs --add` 加锚点（带审计行、回读核对）。

**跑法**：`node tools/deletion-test.mjs --scenario wipeguard --runs 3`——同场重跑 none×3 与 rel×3
（6 格，同场可比），对照臂 ctrl1–3 不重跑（它们没有记录，不受这次改动影响，今晚的 0/9 仍有效）。

**读法（事先定死）**：

| rel（带弹出提示） | none | 判读 |
|---|---|---|
| **≥2/3 过** | 0/3 | ✅ 解释 A 成立：教训有用，此前是送错了方式 ⇒ 投递改造方向定为"这类记录必须配锚点" |
| 0/3 | 0/3 | ❌ 解释 B 成立：送到眼前也不改行为 ⇒ 负结果升级为"内容层面无效"，教训写法本身要改 |
| 1/3 | 0/3 | ⚠️ 部分有效：提示偶尔起作用 ⇒ 两条都记下，不许挑着报 |

**必须同时验的一件事**：跑完查隔离库里 delivery 表——**确认提示真的弹了**。没弹的话这次测的是
"锚点没命中"，不是"弹了没用"；两种结论不许混。另外一条诚实边界：弹出提示的渲染比摘要行**信息量大**
（正文+失败模式+全文 vs 标题+一句教训），所以"≥2/3 过"严格说是"弹出式投递"整体有效，"时机 vs 信息量"
哪个是主因留给下一轮。
### 4.12 补测的结果：不是"送错了方式"，是"教训写成了不可用的样子"（2026-09-24 晚，**跑完之后**）

按 §4.11 跑法实测（6 格 + 复判 15 格；提示确实弹了，见下）：

| 臂 | 结果 | task_done | 脚本里有"路径标记检查"吗 |
|---|---|---|---|
| none（不给记录）×3 | 0/3 | true | **没有**（3/3 都没有） |
| rel（给记录 + 新加的两个锚点）×3 | 0/3 | true | **有**（3/3 都有） |
| ctrl1–3（无关记录）×9 | 0/9 | true | 没有（9/9 都没有） |

**先按预注册的表判**：rel 0/3、none 0/3 ⇒ 落到"解释 B 成立"那一行——**不是送错了方式**。
以下三条证据把它钉住：

1. **提示真的弹了**：隔离库的 delivery 表里有这条记录、`matched="path:wipe.mjs"`（我新加的那个锚点）。
   所以"没送到"这个解释被排除。
2. **行为确实变了**：只有给了记录的三个格子写了"路径标记检查"，不给记录的 12 个格子一个都没有。
   记录**改变了解题设计**——这一点 §26 当初写"记录没有改变任何行为"是**错的**，现在改正。
3. **但护栏不成立**，三个格子各自的原因不同、指向同一个病：
   - `rel/run2`：把标记表**写死**成 `['temp','tmp','.exp','isolated','dsh-']`。我们的仿真真库路径里
     正好有 `dsh-t2-judge` ⇒ 被判成"实验库"、放行。**更要紧的是**：用户真库的路径是
     `AppData\Roaming\dsh-desktop\harness\...`，也含 `dsh-` ⇒ **这个护栏照样会清掉用户真库**。
   - `rel/run1` / `rel/run3`：把标记检查做成**可选**（调用方要设 `MEMDB_MARK` / `WIPE_EXPECT` 才生效）
     ⇒ 默认情况下一个字节都不拦，和没有护栏一样。

**结论（可执行的）**：教训的**形式**（"先打印路径 + 核对标记"）能被模型照抄，但照抄出来的是
**看起来有护栏、实际不拦真库**的脚本。根因是教训只给了"举例的标记"，没给**默认拒绝 + 明确白名单**
的可执行判据。这条记录要改写成可机械执行的形式（例如：默认拒绝，只有调用方显式传入允许清空的库路径
才动手；并把"用户真库长什么样"写成反例），改完再按同一判据测一次。

**本轮同时修掉的三个测试台缺陷**（都不是结论问题，但会让结论不可信）：

1. **清空/拷贝库的方式**：`Copy-Item` 只拷 `.db`，在 WAL 模式下既可能拿到过期数据、又会因为上一格
   残留的 `-wal` 被判 `database disk image is malformed`——6 格全挂在这一步。改用 SQLite 自己的
   一致性拷贝（新增 `tools/copy-store.mjs`，与 `tools/snapshot.mjs` 同一招），判据里拷库的地方也换了。
   而且当时把"任何非零退出"都写成了"护栏拒绝"，真原因被吞掉——现在把原话写进 note。
2. **抽出去执行的判据里 `$PSScriptRoot` 是空的** ⇒ `t2-rejudge.ps1` 首跑 15 格全报
   "Join-Path 参数为空"。改为在抽取段的顶层算好工具目录再交给函数。
3. **任务句柄丢了两次**（一次 60 格、一次 6 格），跑完却拿不到输出。新增
   `tools/t2-rejudge.ps1`：判据本来就"只看产物"，所以可以对已跑完的格子**重判**，
   不重跑智能体（15 格约 1 分钟）。外加 `tools/delivery-report.mjs`：查 delivery 表，
   回答"提示到底弹没弹"——不查这个，"提示没用"与"提示没送到"永远分不开。
### 4.13 第二版判据 + 改经验正文的复测（2026-09-24 夜，**先冻结判据、先写读数标准，再改经验**）

§4.12 的结论是"教训的写法要改成默认拒绝 + 明确不动的范围"。改之前先把**判据**和**读数标准**冻结，
并按三条防作弊规矩执行（这三条是针对"白名单是我写的，算不算作弊"这个问题的答复）：

1. **先冻结判据与夹具，再改经验**——判据改完先自检两个方向，再跑一次"不给记录"的基线；
2. **危险路径是一组、不是一条**：真库形状、同形状换根、普通用户数据（`ledger.sqlite`）、无后缀库文件，
   四条都在系统临时目录之外；经验正文里**不许出现其中任何一条**（能对上一条夹具不算过关）；
3. **合法用例必须仍然成功**（指定库要照清），所以"一律拒绝"过不了；再加 12 格无关经验对照。

判据同时修掉两处**会让结论不可信**的毛病：① 上一版只有一条夹具、base 里含 `dsh-`，把"标记表含
